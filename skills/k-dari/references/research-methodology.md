# 연구 방법론

## 1. 질문 설계

`docs/QUESTION_ROUTING.md`에 따라 주 유형·보조 유형, 응답 모드, 확인 질문, 한국 맥락 여부를 먼저 정한다. 분석 대상, 목적, 기준일, 관할권, 비교 범위, 독자, 검증 질문을 한 단락으로 고정한다. 대상이 불명확하면 조사 전에 필요한 식별정보만 묻는다.

간단 질문은 `QUICK`, 일반 평가·비교는 `STANDARD`, 사용자가 심층 조사를 명시하면 `DEEP_RESEARCH`를 선택한다. PDF와 외부 API 키는 기본 시작 조건이 아니다.

## 2. 유형별 프레임워크

`docs/RESEARCH_FRAMEWORKS.md`에서 선택된 유형만 적용한다. 법률·코인·네트워크·백서·스테이블코인·토큰증권·거래소·사업모델을 하나의 토큰증권 프레임으로 합치지 않는다.

## 3. 사업모델 해부

고객·이용자, 가치제안, 기술 구조, 기초자산, 수익원, 핵심 사업자, 발행·유통, 보관·결제, 권리행사, 실패 시 책임, 위험을 표로 정리한다. 기술 설명과 법적 권리의 원천을 혼동하지 않는다.

## 4. 해외 규제

관할권, 규제기관, 적용 법률, 인가·등록, 운영 조건, 변경 이력, 불확실성을 기록한다. 사례의 발행일과 규제 시행일을 비교해 해당 규제가 실제 적용되었는지 확인한다.

## 5. 한국 규제

법률 → 시행령·규정 → 감독기관 발표 → 국회 동향 순으로 확인한다. 조문과 부칙의 시행일을 별도로 기록한다. 법률상 증권의 “내용”과 토큰이라는 “형식”을 분리한다.

한국을 명시하거나 국내 사업·이용·거래소와 직접 관련될 때만 적용한다. 연결이 약하면 해외 제도·프로젝트 자체를 중심으로 설명한다.

## 6. 격차 분석

관련성이 있는 항목만 비교한다: 법적 분류, 원장 효력, 발행·공시, 인가, 유통시장, 보관, 결제·정산, AML/KYC, 투자자 접근, 운영·사이버 위험, 도산절연.

## 7. 시사점

각 결론을 `확인된 사실`, `근거 있는 추론`, `사업 기회`, `실행 제약`, `필요 조건`, `추가 조사`로 나눈다. 기회에는 수익 주체와 고객을, 제약에는 해소 조건과 책임 주체를 적는다.

## 8. 보고

국문 본문은 결론 선행으로 쓴다. `QUICK`에는 보고서 템플릿과 Evidence JSON을 강제하지 않는다. `STANDARD`는 주요 공식 출처와 사실·주장·추론·미확인을 구분한다. `DEEP_RESEARCH`는 Evidence ID를 문장 또는 표 셀에 붙인다. 영문 Executive Summary는 한국어 보고서의 범위를 넘는 새 사실을 추가하지 않는다.

## 9. 재현 기록

검색 도구, 공식 원문 URL, 원문 형식, 조회시각, 해시, 자동·수동 검증 결과를 research log에 남긴다. 검색 결과 요약은 공식 원문 후보 탐색에만 사용한다. 새 사례 검증에서는 기존 사례 문장을 재사용해 사례명만 바꾸지 않는다.
